# CS-WebUI 2.5.0-beta.4.7

## Official WebUI nightly efac0e24d

Official WebUI 2.5.0-beta.4 assets are refreshed to upstream commit
`efac0e24dd4e6199dd7308c485906c90fb8816a2` (nightly CI run 38617319312), which
contains the upstream fixes for three CS-WebUI reports:

- webui-dev/webui#721 (`9f36ede5d`): calls that arrive together no longer
  share one event slot.
- webui-dev/webui#720 (`dc888150c`, `4e65ad711`): a reply after `webui_exit()`
  with asynchronous responses no longer reads a freed event. WebUI keeps an
  event it stopped waiting for and ignores the late reply; an empty
  `webui_return_string()` now completes an asynchronous call.
- webui-dev/webui#722 (`2456744e6`): `webui_script()` releases its response
  buffer under WebUI's lock before it returns, so a result that arrives after
  a timeout is discarded instead of being copied into the buffer. A result
  that does not fit is now cut to the buffer size less one byte and always
  null-terminated (previously the full buffer, without a terminator). WebUI
  also checks each argument length of a call against the bytes left, so a
  call whose lengths wrap in their sum is dropped with an empty reply.

Further upstream fixes since `4e65ad711`:

- `657813fc8`: a timed-out `webui_script()` id stays reserved until its late
  result arrives or the client closes, so a late result cannot complete a
  later call that reused the id; a pending call fails when its client closes
  instead of waiting for the timeout.
- `926e493f4`: the state for a message split into several WebSocket frames is
  kept per connection instead of shared, and a message is still limited to
  `WEBUI_MAX_BUF` (64,000,000 bytes); the HTTP handler no longer leaves its
  lock held after an invalid client.
- `efac0e24d`: bounded string concatenation and JavaScript bridge formatting,
  Firefox `profiles.ini` matched and rewritten by whole lines and sections,
  file paths and queries quoted as single shell arguments for the Deno, Bun
  and Node runtimes, and Windows command output read while the process runs.

The C header and its 112 exports are unchanged since `4e65ad711`; only
`src/webui.c` changed.
CS-WebUI keeps its own shutdown protection, which `webui_clean()` still needs.
Shutdown stress against the official linux-x64 binaries, 300 host processes
each, 8 in parallel:

## Strings and buffers passed to WebUI

An audit for webui-dev/webui#717 found every managed string passed to WebUI
already null-terminated and rejecting embedded null characters. Further:

- `WebUiResult.FromString` and the implicit conversion from `string` reject
  an embedded null character when the result is created, rather than when it
  is sent. **Compatibility:** the implicit conversion can now throw
  `ArgumentException`, for example in `return text;` from a binding.
- `WebUiEvent.GetString`, `GetInt64`, `GetDouble`, `GetBoolean` and
  `GetBytes` read an argument with the byte length WebUI received.
  **Compatibility:** `GetString` now also returns the text after a null
  character sent from JavaScript, where it used to stop there, and
  `GetInt64`, `GetDouble` and `GetBoolean` parse the whole argument, so an
  argument such as `"12\0x"` now fails with `FormatException` instead of
  reading `12`.
- WebUI checks a call's argument lengths only by their sum, which can wrap.
  The argument getters now throw `InvalidDataException` for a call in which
  an argument claims more than WebUI's 64,000,000-byte message limit, instead
  of reading past the received bytes.
- `WebUiApplication.SetBrowserFolder` rejects control characters, double
  quotes and shell-expanded characters, like `SetBrowserPath`: WebUI starts a
  browser found in that folder through the shell. `SetBrowserPath` reports a
  path containing a null character instead of failing in `Path.GetFullPath`.
- `WebUiWindow.ExecuteJavaScript` uses a native response buffer. WebUI before
  `2456744e6` copies a result that arrives after the timeout into the buffer
  it was given, which was previously an unpinned managed array. Each call with
  a finite timeout that fails now keeps its buffer (`responseBufferSize`
  bytes) until `WebUiApplication.Clean` releases WebUI's state.
  **Compatibility:** with WebUI `2456744e6` and later, a result that does not
  fit is one byte shorter than before (`responseBufferSize` - 1 bytes).

With the bundled WebUI `efac0e24d`, the kept response buffers and the
argument length check are redundant: WebUI no longer writes after
`webui_script()` returns and drops such calls itself. Both stay, for a WebUI
loaded through `CSWEBUI_NATIVE_LIBRARY` that predates these fixes.

## Also since 2.5.0-beta.4.6

- `StartServer` fails when WebUI returns an empty URL, and takes server ports
  from the operating system.
- `WebUiApplication.Exit` and `Clean` discard asynchronous replies once WebUI
  has released their events; show failures name the browser that was tried;
  `SetBrowserPath` and `CSWEBUI_BROWSER_PATH` select one browser executable.
